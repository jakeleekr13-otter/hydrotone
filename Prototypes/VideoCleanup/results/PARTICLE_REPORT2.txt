  1 cell is 0.1 point worse: S3 particle>denoise drift, -57.5 % -> -57.4 %.
- Fish survive in both particle-only and particle-then-denoise. The crops are in section 5.

7. RISKS
1. Memory build-up in the caller. A Core Image render keeps its input buffers until the
   autorelease pool drains. Without a pool per frame, memory grew 16.6 MB per 1080p frame
   (mode leak: 1120 -> 4110 MB in 240 frames; with a pool: flat at 140 MB).
   This also happens with the old filter (mode drift, V1). At 4K each peak buffer is 66 MB (3840 x 2160 x 8 bytes).
   VideoExporter.swift renders outside its autorelease pool. When the filter is added, wrap
   the per-frame push and render in autoreleasepool. The bench now does this in its speed loops.
2. Speed varies with the GPU clock and with other GPU users. The minimum seen on the final
   build was 125.9 fps, close to the 120 target. A longer export on this fanless Mac may slow
   down more. Not measured beyond 900 frames.
3. iPhone speed is unmeasured. The code typechecks for iOS 26 with Swift 6 and warnings as
   errors. It has not run on a device.
4. Output lag is now 3 frames, not 2. push/finish handle it; tested with 0 to 6 frames (mode edges).
   Code that assumes a fixed lag would break.
5. push calls waitUntilCompleted. This SDK marks it unavailable in async code. push is a plain
   sync function, so it compiles. It must not become async without changing this wait.
6. Output is not bit-identical to the old filter (section 2). Segment metrics moved by 0.3 points or less.
7. The coarse search keeps a row in threadgroup memory. It handles frames up to 8384 px wide.
   Wider frames get no motion and pass through unfiltered.
8. Frames of another size than the first still pass through at once, out of order. This is unchanged from the old version.
